Which participant count belongs with each posted trial result?

Animesh Bose, Norlowe Research

Evidence tables built from ClinicalTrials.gov need the number of people behind every value. The registry records counts at the outcome and table-row levels and sometimes in other units. The comparison export used here keeps one count per arm and outcome. I built a PostgreSQL warehouse that keeps every level, and measured how often the right count can be attached by written rules in 1,961 cardiometabolic trials. For 23.0% of 97,756 held-out measurements, the flat export attached the outcome-level count although the table row reported a different number analyzed.

Research question. Among interventional diabetes, heart failure and obesity trials with results first posted from January 2020 to September 2026, how often can a documented participant denominator be kept and attached to each reported value without guessing, and what does a one-row-per-value flat export lose or attach instead?

One frozen snapshot held 2,615 studies, and 2,469 were confirmed for a condition group

I queried the ClinicalTrials.gov API (version 2.0.5, data timestamp 2026-10-06T09:00:05 UTC) for interventional studies under "diabetes mellitus", "heart failure" and "obesity" whose results were first posted between January 2020 and September 2026. All 2,615 studies were retrieved and saved with SHA-256 hashes. A fixed vocabulary rule confirmed 2,469 of them for at least one condition group and set aside 146 studies whose condition entries and MeSH terms did not meet the rule. Only public aggregate results were analyzed. The point-of-contact block of each results section was not loaded, and no registry contact details are redistributed.

Rules were written on one part of the data and run once on the rest

Before reading any results, I grouped studies by shared identifiers and split them by hash into a development portion (508 studies) and a held-out portion (1,961 studies). The loader, the rules and the checks were built and reviewed on the development portion, then frozen by file hash. The held-out audit ran once with that frozen code. The program refuses a second primary run and allows only a logged reproducibility rerun, which gave identical outputs.

Each outcome group gets a tier. A means the count is given once per group at the outcome level. B means a written rule is needed, mostly because the table's rows carry their own number analyzed, which then takes precedence. C means no count can be attached without unsupported inference, for example when the count is "NA". D means the outcome was not posted or the group has no values. The rules are in rules.md.

The flat export is a declared design, and groups are never linked by label

The flat export follows the common pandas json_normalize convention: one row per value, every value kept as text, every ancestor field copied down to the row, and the outcome-level participant count attached to each row. Its losses come from that declared design; a flat file with extra columns for row-level and unit counts would keep more. A declared export was needed because the registry's own CSV download carries no posted results data, only a flag for whether results exist and the date they were first posted.

Groups are never linked across modules by label. The same code, OG000, carried different group titles in different outcomes in 377 of 1,770 studies (21.3%) that used it in two or more outcomes, and an identical baseline group title carried a different participant count for 18,645 of 34,784 outcome groups (53.6%) whose two counts were both usable. The warehouse lists same-titled groups for context and leaves the link to a person.

Most counts are there, but one group in seven needs a row-level or unit-specific count

Of 43,715 applicable outcome groups, 37,592 (86.0%) were tier A and 6,118 (14.0%) tier B; only 5 outcome groups could not be given a count. At the level of single values, 35,378 of 97,756 measurements (36.2%) needed a rule. The flat export also had no row for the 1,847 of 19,957 outcomes (9.3%) that had no posted values, so their groups and descriptive fields were lost. It returned 1,162,192 of the 1,342,202 source values it attempts (86.6%) exactly, and it lost every row-level denominator and every reason a participant did not complete.

In one held-out outcome, row-level counts ran from 0 to 77 under an outcome-level count of 77 per group

In NCT02443155, the outcome "Occurrence of Anti-NNC0114-0006 Antibodies" reports 77 participants in each of its 2 groups, while its rows report numbers analyzed from 0 to 77. A flat export attaches the outcome-level count to every one of these rows, including rows where only 2 participants were analyzed.

The warehouse returned every in-scope source value

I wrote a separate program in R that read the same raw records and enumerated every value with its JSON pointer. The warehouse matched all 2,502,817 in-scope values exactly, the two implementations agreed on the tier and denominator of all 97,756 measurements, and all 9,805 results modules rebuilt from the warehouse were identical to the source. Reloading the snapshot, rebuilding it in a second database and rerunning the held-out analysis gave identical outputs.

Twelve checks for possible source inconsistencies ran only where units and populations permit. Of 536,743 applicable checks, 16 failed and 314 could not be evaluated; most failures were negative values labeled as percentages of participants. Each sits in the issue ledger with its source location; none is a confirmed error.

Limitations

  • The R reference was written separately but follows the same written rules, so a shared misreading of the rules would not show up.
  • The rules decide which count applies from the record's structure. They do not show that a registry entry is clinically correct, and no external gold standard exists.
  • The study covers three condition groups and one snapshot of a registry that changes, and the API offers no programmatic access to earlier record versions. The recall of the registry's condition search was not assessed.
  • The flat export is one declared design. A flat file with extra columns for row-level and unit counts would not misattach these counts.
  • The measurements whose row reported a different number analyzed were concentrated in a minority of studies (post hoc).
  • Percentages describe this held-out corpus. They are not estimates for all registered trials, so no confidence intervals are attached.
  • The REDCap review instrument is a template for future adjudication. No ledger item has been adjudicated yet.

Reproduce the analysis

The source archive needs Python 3.12 or newer, R with jsonlite, and PostgreSQL 17 binaries; the project starts its own database inside its folder. I tested it on macOS with Python 3.13.5, R 4.5.1 and PostgreSQL 17.11. It is written to run on Linux too, but I have not tested it there.

python3.13 -m venv .venv               # any Python 3.12 or newer
.venv/bin/python -m pip install -r requirements.lock
.venv/bin/python -m pip install -e . --no-deps
.venv/bin/python -m pytest -q          # software tests on synthetic fixtures
.venv/bin/python -m tra demo           # short demo on the fixtures (starts the project database)
.venv/bin/python -m tra acquire        # retrieves the registry as it is today
.venv/bin/python -m tra freeze
.venv/bin/python -m tra build --split development --fresh

Rerunning the retrieval returns the registry as it is on that day. The exact pages analyzed here are identified by URL and hash in source_manifest.json.
